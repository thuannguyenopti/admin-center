AI-Generated Content Quality Rubric

A shared evaluation framework for assessing whether Opal-generated pages meet production quality. Based on analytic rubric design principles (Allen & Tanner, 2006) with domain-specific criteria for the Optimizely design system, brand packs, and content standards.

Scope: Opal page generation Version: 1.0 Date: 2026-07-03 Dimensions: 5 Criteria: 18

Scoring Levels

Each criterion is scored on a three-point scale. Descriptors are cumulative: "Excellent" assumes all "Acceptable" conditions are also met.

3 — Excellent

Ready to publish. Indistinguishable from hand-crafted content by a senior designer or editor.

2 — Acceptable

Usable with minor edits. Meets baseline requirements but has noticeable gaps a reviewer would flag.

1 — Poor

Requires significant rework. Structural, visual, or content issues that would block publication.

Quality Rubric

18 criteria grouped into 5 dimensions. Weights reflect relative importance to overall page quality. A page must meet the pass threshold defined below to be considered "good quality."

Dimension Criterion 3 — Excellent 2 — Acceptable 1 — Poor
1. Visual & Layout Correctness 30%
Visual & Layout Spatial consistency
  • All spacing uses Axiom tokens (4, 8, 12, 16, 20, 24, 32)
  • Consistent vertical rhythm across sections
  • No pixel-level misalignment between siblings
  • Most spacing uses tokens; 1–2 arbitrary values
  • Minor inconsistency in section gaps
  • Hardcoded pixel values throughout
  • Irregular spacing with no visible rhythm
  • Overlapping or clipped elements
Responsive behavior
  • Layout reflows cleanly from desktop to mobile
  • Grid uses minmax() and auto-fill/auto-fit
  • No horizontal scroll at any breakpoint
  • Desktop looks correct; mobile has minor overflow or tight spacing
  • Breakpoints exist but some elements don't resize well
  • Fixed-width layout that breaks below 768px
  • Content overflows or is inaccessible on smaller screens
Visual parity
  • Generated page is indistinguishable from an existing hand-built page in the same product area
  • Matches established hero/card/section patterns in the codebase
  • Recognizably "Opal" but with stylistic inconsistencies (e.g., wrong border radius, shadow level)
  • Looks like a generic template; does not resemble existing Opal pages
  • Mixes design languages or introduces novel patterns
Color & theming
  • All colors use semantic tokens (fg.*, bg.*, border.*)
  • Opal gradients use --opal-gradient-* custom properties
  • Dark mode renders correctly via [data-theme="dark"]
  • Mostly semantic tokens; 1–2 hardcoded hex values
  • Dark mode partially works but some elements are unreadable
  • Hardcoded hex colors throughout
  • No dark mode support or contrast failures
2. Component Composition 25%
Component Composition Axiom component usage
  • Every interactive and layout element uses an Axiom component (Button, Input, Box, Text, Badge, etc.)
  • No raw HTML <button>, <input>, <select>, or <div> for product UI
  • Core elements use Axiom; 1–2 instances of raw HTML for edge cases
  • All interactive controls are Axiom
  • Significant use of raw HTML elements alongside Axiom
  • Custom-styled buttons or inputs that bypass the design system
Prop correctness
  • Props match Axiom API (e.g., appearance="primary", size="md")
  • No invalid prop values (e.g., size="sm" on Input)
  • Icons from correct package (@optiaxiom/icons for Opal)
  • Props are valid but not optimal (e.g., missing appearance, default sizes everywhere)
  • Invalid prop values causing console errors or visual breakage
  • Wrong icon package or missing icons
Pattern adherence
  • Uses established codebase patterns: usePersistentState, useLayout, Field wrappers, Menu with options prop
  • No legacy patterns (e.g., DropdownMenu instead of Menu)
  • Follows Box asChild pattern where needed (no Box as="span")
  • Most patterns correct; one legacy or anti-pattern present
  • Introduces new patterns that conflict with established conventions
  • Hydration errors from incorrect nesting (e.g., <div> inside <p>)
Accessibility
  • All interactive elements have accessible names (labels, aria-label)
  • Keyboard navigable; focus order matches visual order
  • Sufficient color contrast (WCAG AA)
  • Images have meaningful alt text
  • Most elements accessible; 1–2 missing labels on icon-only buttons
  • Color contrast passes in light mode
  • Multiple unlabeled controls or non-focusable interactive elements
  • Color-only information with no text fallback
3. Structural Consistency 15%
Structural Consistency Section completeness
  • All required sections present (hero, body, CTA) per template specification
  • Section order matches template definition
  • No empty or placeholder sections
  • Required sections present; order slightly rearranged but still logical
  • One optional section missing
  • Missing required sections (e.g., no CTA, no hero)
  • Placeholder text like "Lorem ipsum" or "[Insert headline]"
Template fidelity
  • Aspect ratio matches template spec (1:1, 4:5, 16:9, etc.)
  • Grid column count and layout matches template
  • Component types match template slots (e.g., image where image expected)
  • Overall shape matches; minor deviations in grid or ratio
  • Output bears little resemblance to the selected template
  • Wrong aspect ratio or completely different layout structure
Information hierarchy
  • Clear heading levels (H1 → H2 → H3) with no skips
  • Visual weight matches importance: primary CTA is prominent, secondary actions are subtle
  • Content flows logically top-to-bottom
  • Heading hierarchy present but one level skipped
  • CTA visible but not obviously the primary action
  • No heading hierarchy; all text at same visual weight
  • CTA buried or competing with secondary actions
4. Content Relevance 15%
Content Relevance Topical accuracy
  • All copy is on-topic and specific to the product/feature described
  • No hallucinated features, pricing, or capabilities
  • Statistics and claims are plausible and internally consistent
  • Mostly on-topic; 1–2 vague or generic sentences that could apply to any product
  • Fabricated product details or features that don't exist
  • Generic filler text unrelated to the intended topic
Content depth
  • Body sections contain substantive detail (not just headlines)
  • Feature descriptions include benefit statements
  • Word count appropriate for channel (e.g., ≥150 words for web pages)
  • Content is present but thin; some sections feel like outlines
  • Headline-only content with no supporting detail
  • Significantly under target word count
Channel appropriateness
  • Tone, length, and format match the target channel (Social, Email, Web, Paid)
  • Social: concise, hook-driven. Email: scannable, CTA-focused. Web: detailed, SEO-aware
  • Broadly appropriate but some channel conventions missed (e.g., email is too long)
  • Content written for wrong channel (e.g., social-length copy on a landing page)
Localization readiness
  • No hardcoded strings that would block i18n
  • Date/number formats are locale-neutral or parameterized
  • Text fits containers at 130% expansion (typical for DE/FR translations)
  • Most strings externalizable; a few inline hardcoded labels
  • Strings baked into layout with no extraction path
  • Tight containers that overflow with longer translations
5. Brand Alignment 15%
Brand Alignment Tone & voice
  • Copy embodies all tone keywords defined in the Brand Pack (e.g., "Bold", "Energetic")
  • Follows voice rules: active verbs, second person, outcome-led
  • Avoids all "avoid" examples from the tone config (no jargon, no inflated AI claims)
  • Tone is broadly correct but misses 1–2 keyword dimensions
  • Occasional passive voice or feature-led (not outcome-led) phrasing
  • Tone contradicts brand pack (e.g., corporate and stiff when pack says "Bold")
  • Uses explicitly flagged "avoid" phrases
Visual brand
  • Colors match Brand Pack palette (primary, secondary, accent applied correctly)
  • Typography uses configured heading + body fonts
  • Logo/wordmark present in correct position per brand brief
  • Assets (photos, icons) are from the Brand Pack asset library
  • Primary color correct; secondary/accent slightly off
  • Logo present but placement deviates from brief
  • Colors unrelated to brand pack
  • Wrong or missing logo; off-brand imagery
Brand brief compliance
  • All explicit rules in the brand brief are followed
  • Content targets only approved channels defined in the Brand Pack
  • Messaging aligns with brand positioning statement
  • Brief mostly followed; one non-critical rule missed
  • Brand brief rules ignored or contradicted
  • Content published to unapproved channel

Pass / Fail Threshold

A generated page is considered "good quality" when all of the following are true:

  • No criterion scores 1 (Poor) — any Poor score is a blocking defect that requires rework.
  • Weighted average ≥ 2.5 — calculated as: ∑(dimension_avg × weight). A page at exactly 2.0 across all dimensions is functional but not publishable without review.
  • All blocking checks pass — Brand Pack has colors defined, typography configured, and at least one tone keyword (mirrors the existing TestPublishTab gate).
  • Accessibility floor — no WCAG AA contrast failures, all interactive elements keyboard-reachable.

How to Use This Rubric

Context Method Outcome
Manual review Reviewer scores each of the 18 criteria 1–3 using the descriptors above. Takes 5–10 minutes per page. Scorecard with per-dimension averages and overall weighted score. Pages ≥ 2.5 pass; others get a list of specific criteria to fix.
Automated lint Criteria from dimensions 1–3 (Visual, Component, Structure) are checkable via AST analysis, Axiom lint rules, and accessibility scanners. CI gate that flags poor-scoring criteria before human review. Reduces manual effort to dimensions 4–5 (Content, Brand).
LLM self-evaluation Pass the rubric as a system prompt to Opal. After generation, Opal scores its own output and flags any criterion below 3. Self-improvement loop: Opal re-generates sections that scored 2, surfacing only ≥ 2.5 pages to the human reviewer.
A/B comparison Score both a hand-built page and an AI-generated version of the same content. Compare per-criterion deltas. Identifies which quality dimensions AI excels at vs. struggles with, informing prompt engineering and template design.

Methodology: Analytic rubric design based on Allen & Tanner (2006), "Rubrics: Tools for Making Learning Goals and Evaluation Criteria Explicit for Both Teachers and Learners," CBE—Life Sciences Education, 5(3), 197–203. Criteria derived from Optimizely Axiom design system conventions, Opal Brand Pack configuration schema, and existing TestPublishTab validation logic.

Maintenance: Review and update this rubric quarterly or when Axiom major version changes. Add new criteria only when an existing dimension cannot capture a recurring quality issue.
